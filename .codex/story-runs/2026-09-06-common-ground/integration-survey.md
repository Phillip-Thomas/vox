### Registration choice

Formalizing the existing visit/return as ch11/ch12 is feasible, but is not a small JSON addition. Every formal beat presently requires an App-style contract, generated metadata, runtime order, objective projection, deep-link/seed/resume behavior and acceptance observations. Station-local objectives do not use the `GuidedStoryObjective` contract, and the station page has no live App story director. A truthful formalization therefore needs an explicit execution-host adapter (`station` versus `world/free-play`) so its formal beat views derive from the **existing** commits and stage functions. The adapter must handle direct entry/resume and the existing physical navigation, not recreate the transaction or call a fake `advanceToBeat` merely for evidence. This is a separate bounded integration packet if selected; preserve all existing receipt strings and keep exactly one owner of each action.

The smallest honest route for this chapter is an explicit, typed station/return transition contract, with ch11/ch12 identity retained in that contract. It connects ch10's existing threshold exit to the next formal chapter's restored-hearth entry, references the existing producers above, and is independently evidenced. Add schema/tool support and tests for that named external transition rather than weakening adjacency checks. Existing direct chapter-to-chapter checks remain unchanged; the transition itself must prove both of its boundaries and its committed receipts.

This is necessary because `main/tools/chapter-registry-gate.mjs::validateAdjacency` currently requires exact predecessor exit/next entry `stateRefs` equality and every next entry requirement in predecessor guarantees. Ch10's actual exit is station-targeted flight. It does not guarantee restored hearth, on-foot Origin or station departure. Do not add those false guarantees to ch10; do not omit the true new entry requirements to get a green gate. The new transition type must retain a strict composed chain with independently checked entry, exit, milestones and source references. The final choice belongs in the production lock, with source/schema/gate and journey coverage explicitly owned.

`main/story-authority.json` also pins runtime ceiling, order and evidence chain. Extend runtime authority only after the signed packet and delegated decision; preserve its release/demo ceiling. New checkpoint rows must match `STORY_MILESTONES` and the literal `storyEntryPoint` clauses because the registry gate parses those exact source declarations. Supported `state:` references in the registry gate are an explicit allowlist: add a runtime producer in `storyBoundaryTelemetry.ts` before adding a corresponding new pattern.

## Save data and reusable physical state

There is no single generic narrative-ledger store. `game/systems/observationLedger.ts` and `accomplishmentLedger.ts` each expose schema version 1, typed reducers, logical sequence ordering, idempotent evidence IDs, serialize/hydrate functions, actor scope and subscriptions. `ledgerEvidence.ts` supplies JSON-safe evidence payloads. `persistence.GlobalSave` already saves/restores both as optional fields, keeping pre-ledger saves readable.

Observations explicitly **must never be story prerequisites**. Use them for noticed evidence, comparisons, doubts and interpretation variants. Accomplishments can record actual committed acts; neither ledger should become a hidden approval switch based on player interpretation. `emergentStoryEvents.ts` is a typed, deduplicated **session** event stream, not persistent storage. New semantic events can be added here or behind a chapter-local typed publisher; do not rely on its in-memory history for resume.

Keep immutable chapter checkpoints as named `story:` milestones. Reusable/reversible stake placement and a worker's current traversal state cannot be represented safely by a growing pile of untyped `placed:N:x:y` milestones. If placement must survive save/reload, use one chapter-local versioned snapshot with bounded slots, world/actor identity, validated numeric poses and explicit retry/hold state. The existing per-world `WorldSave.habitat` pattern is the nearby precedent: add an optional field and explicit save/restore/clear functions in `persistence.ts`, with the new world component resetting/restoring through that boundary. Do not reset somebody else's world state during ordinary entry. If the signed contract intentionally makes uncommitted placements ephemeral, document and test reconstruction instead; the survey does not choose that creative behavior.

Test absent/legacy snapshots, malformed placement data, wrong world/actor, identical event replay, partial retry, completed chapter reload, quit/Continue, explicit restart and deep-link seeding. `restartStory` currently removes story milestones and resets two authored worlds; it does not clear every narrative ledger record. A new chapter must explicitly define its restart behavior instead of assuming those evidence stores were erased. New deep links need the **physical** restored-hearth and Origin prerequisites, including world/ship/camera pose; adding preceding milestones alone is insufficient. Keep `?keep=1` and normal menu Continue paths non-destructive.
